================================================================================
Imperial 2030 - Azure App Service (Deployment Notes)
================================================================================

Deployed by .github/workflows/main_imperial2030.yml on every push to main.
See Imperial2030.Functions/info.txt for the separate notification Functions app,
and linux-deploy.info.txt for the VPS target.


1. REQUIRED APPLICATION SETTINGS
--------------------------------------------------------------------------------
Portal: App Service -> Settings -> Environment variables -> App settings.

  Jwt__Key                    A base64 secret of at least 32 bytes.
                              The server HARD-FAILS at startup outside Development
                              if this is missing, and rejects the key that was once
                              committed to the repo (it is compromised; its SHA-256
                              is blocklisted in Server/Configuration/JwtOptions.cs).

  ConnectionStrings__DefaultConnection
                              SQL Server connection string. A value containing
                              ".db" selects SQLite instead - see Program.cs.

  WEBSITE_RUN_FROM_PACKAGE    1  (already set)
                              Mounts the deployed zip read-only instead of
                              extracting it over the running site.

  AzureFunctionNotificationUrl / AzureFunctionNotificationKey
                              Optional; enables game-started / game-finished mail.

  LOG_DIRECTORY               NOT required. Optional override only - see below.


2. FILE LOGGING ON AZURE - FIXED IN CODE, NO SETTING NEEDED
--------------------------------------------------------------------------------
Not a deployment fix. A separate bug that WEBSITE_RUN_FROM_PACKAGE has been causing
quietly for as long as it has been enabled.

Server/nlog.config used to write to ${basedir}/logs. ${basedir} is inside the
read-only package mount, so the target could never create that directory on Azure -
and an NLog file target that cannot write does NOT fail startup. It silently
produces nothing, which is why this went unnoticed.

Program.cs now calls LogPaths.ApplyToEnvironment() before AddNLog, and
Server/Configuration/LogPaths.cs derives the directory:

  1. LOG_DIRECTORY, if set          -> used as-is (explicit override)
  2. else WEBSITE_SITE_NAME is set  -> %HOME%/LogFiles
  3. else                           -> <application directory>/logs

Nothing is hardcoded. HOME is whatever App Service exposes - "/home" on Linux, a
drive-rooted path on Windows - so this works on either without anyone having to
know which. WEBSITE_SITE_NAME is set by App Service and nowhere else; gating on it
matters because HOME is also set on Linux desktops and in Git Bash, where it is the
developer's home directory and would otherwise hijack local logs. Covered by
Tests/LogPathsTests.cs.

Also read-only under run-from-package: the SQLite fallback in Program.cs writes
imperial2030.db into ContentRootPath. It is only selected when the connection
string is empty or contains ".db", so Azure (SQL Server) never takes that path -
but a deploy without ConnectionStrings__DefaultConnection would fail there.


3. INTERMITTENT DEPLOY FAILURE
--------------------------------------------------------------------------------
  Error: Failed to deploy web package using OneDeploy to App Service.
  Internal Server Error (CODE: 500)

MEASURED 2026-09-04. Kudu's deployment history (/api/deployments on the SCM site)
contains ONLY successes - no status:3 entry exists for any failed run. A deploy
that had reached Kudu and failed would be recorded there.

So the failure happens BEFORE Kudu: in the ARM/upload handoff, not in the app, not
in its storage, and not in the deployment pipeline. Nothing on the app side of that
boundary can explain it, and nothing on the app side needs changing to fix it.

That also matches the failure being intermittent - a transient fault in the upload,
rather than a resource that has run out.

Mitigation: the workflow retries the deploy once and fails the job only if both
attempts fail. That is the right shape of fix for a transient upload fault. It is
the only thing this repo can do about it.

For reference, storage was checked and ruled out: the F1 plan holds this app alone
against a 1 GiB limit and read 455.49 MiB (~44%). Run-from-package does keep a zip
per deployment under %HOME%\data\SitePackages and that does grow - roughly five
more deploys of headroom at ~100MB each - so it is worth pruning via Kudu eventually
(Debug console -> data/SitePackages, keep packagename.txt and the zip it names).
It is a future capacity note, not a cause.
