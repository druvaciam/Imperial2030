# Agent Rules

- **Cleanup Temporary Files:** Always proactively remove any temporary scripts (e.g., Python scripts, text files) or intermediate media files (like extracted PNGs) created during debugging or troubleshooting before concluding a task.
- **Backend Bugfixes (Test-Driven):** When fixing a bug on the backend, always write a failing test first to reproduce the issue, verify that it fails, then implement the code fix, and finally run the test again to ensure it passes (green).
- **Cross-Platform Compatibility:** Ensure all written code (including scripts and file paths) is fully compatible and works seamlessly across both Windows and Linux operating systems.
- **Build Before Completion:** Always compile/build the project to ensure there are no compilation errors before reporting that a task is done.
- **Extract Constants:** Always extract constants to avoid magic numbers and strings.
- **Run Tests on Backend Changes:** Run targeted tests (e.g., dotnet test --filter <SpecificTest>) during development, and only run the full test suite (dotnet test) during final verification before completing a task.
- **Entity Model Changes & Migrations:** When adding or modifying public properties on EF Core entities, never leave them half-done. Explicitly mark runtime/transient properties with `[NotMapped]` or, if they are intended to be persistent database columns, always generate both EF Core migration files (`SqliteApplicationDbContext` and `SqlServerApplicationDbContext`). Migrations must be applied automatically from code on application startup (via `DbSeeder.SeedAsync` / `context.Database.MigrateAsync()`) and never require manual `dotnet ef database update` CLI commands, ensuring zero-configuration deployments across Azure App Service, Windows, and Linux VPS servers.
- **Diagnose & Report Errors First:** When troubleshooting runtime errors, bugs, or crashes, always inspect logs, terminal output, or stack traces to identify the exact root cause first. Present the factual error diagnosis clearly to the user before making code changes or guessing fixes.
- **Plan & Approval Required for New Features:** Never begin coding or implementing any new feature, architectural change, or non-trivial modification without first writing a detailed implementation plan (`implementation_plan.md`) and obtaining explicit approval from the user.
- **Verify & Maintain Comments in Modified Areas:** Whenever modifying or refactoring code, inspect surrounding and inline comments in the affected scope. Preserve valid comments, update comments that need adjustment to reflect code changes accurately, and remove comments only if they are genuinely obsolete or no longer applicable. Never silently drop or strip valid inline comments during refactoring.
- **Preserve Existing Logging & Telemetry:** Never comment out, remove, or alter log statements (e.g., `_logger.LogInformation`, `_logger.LogWarning`, `_logger.LogError`, console outputs, or telemetry) without explicit instruction from the user. Logging is essential for user inspection, progress monitoring, and debugging.
- **Strict Scope Discipline & No Unsolicited Suppressions:** Never suppress, comment out, disable, or bypass working features, debug logs, or diagnostics to reduce terminal output, optimize I/O, or silence warnings unless the user explicitly requests it.
- **No Speculative Feature Expansion or Hallucinated Action Spaces:** Never invent, expand, or hallucinate action spaces, decision branches, policy masks, or training overrides based on speculation or ungrounded assumptions. All logic and bugfixes must strictly adhere to the actual codebase architecture and explicit user specifications.
- **Game Rules Are Imperial 2030, Not Classic "Imperial":** The authoritative rules are `Imperial-2030-Rules.pdf` at the repo root. This is a *different, rebalanced* game from the classic 2006 "Imperial" board game — it has only six nations (Russia, China, India, Brazil, USA, Europe), not Imperial's Austria-Hungary/Italy/France/Germany/Great Britain/Russia. When reasoning about or implementing game mechanics, verify against the PDF rather than assumption or general "Imperial"-family knowledge — a hallucinated comment referencing a nonexistent "Austria/Europe" investor card was a real bug caused by exactly this confusion.
- **Always Preserve Old RL Model Performance:** When changing RL training/inference code (`RLBotStrategy.cs`, `TcpTrainingServer.cs`) in ways that touch the state vector or action space, existing already-trained `.onnx` models must keep working at their original, undegraded performance — never silently fall back to random or heuristic play. Concretely: only ever *append* new floats/actions at the end of the existing layout (never splice into a per-nation loop or insert before other fields — that reindexes everything downstream and breaks byte-for-byte compatibility with what old models were trained on), and add a matching size guard at the point of ONNX inference (compare the loaded model's actual input/output width against the current vector/action-space size) so an older model gets a truncated prefix — a byte-for-byte reproduction of its original training input — and runs real inference, instead of silently degrading. After any such change, verify old models are still using inference (not the random fallback) by checking training-server action counters stay non-zero and win-rate tests return to their pre-change baseline.
- **Investigate and Fix Test Failures, Don't Dismiss as Flaky:** When a test fails, always investigate and attempt to fix the underlying bug rather than writing it off as flaky or unrelated to the current change. Exception: tests that assert on inherently probabilistic/statistical outcomes (e.g. `TestRLBotWinRate` or any test asserting an RL self-play win-rate percentage/threshold) can have expected run-to-run variance and don't require root-causing every individual failure the same way — though a pattern of *frequent* failures even there is still worth investigating.
- **EF Core: `.AsSplitQuery()` Required on Multi-Collection `.Include()` Chains:** Any query against `Games` (or another aggregate root) that calls `.Include()` on two or more *collection* navigations (e.g. `Players`, `NationStates`, `TerritoryStates`, `Bonds`, `Units`, `Actions`) must add `.AsSplitQuery()` before the terminal `FirstOrDefaultAsync`/`FirstAsync`/`SingleOrDefaultAsync`/`ToListAsync` call. Without it, EF Core defaults to `QuerySplittingBehavior.SingleQuery`, which joins every included collection into one SQL statement and produces a cartesian-product row explosion (logged as an EF Core warning: "Compiling a query which loads related collections for more than one collection navigation... no 'QuerySplittingBehavior' has been configured"). A single `.Include()` on one collection, or `.Include().ThenInclude()` chains where the `ThenInclude` targets are reference (not collection) navigations, don't need it. When a query ends in `.Select()` projecting into a DTO that never materializes the included collections directly (only `.Count()`/`.Any()`/`.Max()`/sub-`.Select()`s), the `.Include()` calls are dead code — EF Core discards them for projections — so remove them rather than adding `.AsSplitQuery()`. When auditing this codebase-wide, don't rely on eyeballing a single Grep call's output, especially if it reports pagination/truncation — run `python tools/scan_splitquery.py` (exits non-zero on any violation, so it can gate CI), since a truncated manual scan can silently miss the worst offenders. An explicit `.AsSingleQuery()` counts as compliant: it states the intent deliberately, which is what the rule is actually asking for. If you change the scanner, note that `context.Games.Add(...)` is not a query — an earlier version matched it and then swept forward into the *next* statement's `.Include()`s, reporting three violations on lines that contained no query at all.
- **Prefer Existing Data Over New Entities/Fields/IDs:** Before adding a new persisted field, entity, or identifier to solve a problem, check whether properties the domain model already exposes (e.g. `Nation`, `UnitType`, `IsHostile`, territory IDs) are sufficient to distinguish or reconstruct what's needed. Only introduce new schema (new `ActionMetadata`/DTO fields, new entities, raw internal DB IDs exposed in a log/export format, etc.) when the existing domain-meaningful properties genuinely cannot do the job. Concrete example: fixing `GameReplayService`'s unit-matching ambiguity (multiple identical units of the same nation moving in one turn) was first attempted by adding a new `UnitId` (raw internal `Guid`) to the action log — the user rejected this and pointed out the unit's existing `IsHostile` property, already domain-meaningful and already persisted per-unit, was enough to disambiguate without leaking an opaque internal identifier into a portable action-log/export format.
- **Don't Bend Business Logic For Tests or Features:** Never change shared game business logic (`Server/Controllers/*.cs`, `Server/Services/*.cs`, `Server/Helpers/*.cs` — combat resolution, maneuver phases, investment, taxation, etc.) just to make a test pass, or just to make a new feature's implementation more convenient. A new feature (export, import, replay, RL training, etc.) reusing existing endpoints/services must adapt to what those already correctly do, not the other way around — if reuse seems to require a rule change, that's a signal to build the feature differently (a new code path, a parameter, a wrapper), not to reshape shared logic around it. Only change shared logic when the current behavior is a provable, real bug — reproducible, and affecting real gameplay independent of whatever test/feature surfaced it — and say so explicitly, citing the concrete failure mode, not "the test/feature wants this." Concrete example: `ManeuverController.MoveArmy`/`MoveFleet` had a real pre-existing bug where an auto-resolved hostile-move battle logged the move twice (once explicitly, once via a trailing unconditional log call unaware the unit had just been destroyed) — invisible in live play since nothing reconstructs state from the action log there, but it broke replay, which takes the log literally. That was a legitimate fix: the bug was real and independent of the replay feature that happened to surface it. Reshaping `MoveArmy` itself to have a "replay mode" instead would have been the kind of business-logic bending this rule forbids.
- **Don't Fine-Tune Existing Logic's Behavior Just to Satisfy a Test:** A more specific trap than the rule above, because it doesn't feel like cheating: when an existing code path has an underspecified choice (an arbitrary `FirstOrDefault`, an unstated tie-break, an ordering nobody committed to), the instinct is to make it "deterministic" or "sensible" and treat that as a legitimate bug fix. It is not, if the only reason you're touching it is that a replay/test run depends on reproducing one *specific* historical outcome. Changing what live game logic *decides* changes real gameplay for every future game, not just the replay case that prompted the change — and picking a "reasonable-sounding" tie-break (e.g. "prefer same unit type") can still be flat wrong against the actual rules (see `Imperial-2030-Rules.pdf`), just wrong in a way that's harder to notice because it looks principled. The correct fix for "replay can't reproduce an ambiguous historical choice" is almost always to make replay consume information the log already recorded (extend the *replay-only* call site, not the shared decision logic) — never to narrow what live play is allowed to do. Concrete example, same session as the rule above: `MoveArmy`/`MoveFleet` auto-resolve arbitrarily picked which enemy unit type to destroy when a territory held more than one (an Army and a Fleet of the same nation) — replay of a game where this happened could pick a different unit type than the original run and diverge. The first attempt "fixed" this by making the live endpoint always prefer same-type matches — this was wrong to do: it altered real combat resolution (and, per the rulebook, the actual rule is that the *attacker* chooses the target, not the engine), and it was fixing a replay-reproducibility problem by changing gameplay. The actual fix: the log already records which unit type died (`Battle` action's `DefenderUnitType`); `GameReplayService` now looks ahead at the log for that entry before calling `MoveArmy`/`MoveFleet` and passes it in via the existing `BattleTargetNation`/`BattleTargetUnitType` request fields (extending an existing "explicit target" mechanism, not inventing new schema — see the rule above this one), so live play's own auto-resolve logic is completely untouched and only replay's request-construction changed.
- **Never Drop, Defer or Silently Reinterpret a Requested Task:** When the user asks for several things — in one message or across a conversation — every one of them must be delivered, or the omission stated outright. Do not quietly narrow a task, substitute an easier adjacent change, or let an item fall off because a later message arrived; a follow-up message adds to the list, it does not replace it. If a request cannot be completed as asked, say so explicitly and say why, in the same reply — silence reads as "done". If a request is genuinely ambiguous, ask once and then finish it; repeatedly asking for clarification instead of delivering is itself a form of dropping the task. Before ending a turn, re-read the user's outstanding asks and confirm each was either done or explicitly reported as not done. Concrete example: asked to (a) draw cross-edge moves as two segments leaving opposite borders and (b) draw a convoyed army's path through every sea region it crossed, the assistant instead iterated repeatedly on unrelated static map decoration, restated (b) as an open question three times without implementing it, and had to be told five times before either was built.
- **Check Whether It's Logic Or A Hallucination Before Invoking "Don't Touch Game Logic":** The two rules above forbid *bending* correct game logic. They are not a licence to leave incorrect code alone. Before declining to change a behavior on the grounds that it is "existing game logic", first check it against `Imperial-2030-Rules.pdf` — the rulebook is the source of truth, not the current code. Existing code is only "game logic" to be protected when it *matches the rules*; where it contradicts them it is a bug, and the rules above explicitly permit fixing a provable bug. Treating every existing behavior as sacred is the mirror-image failure of bending it: both substitute a reflex for reading the rules. State which rule in the PDF the behavior does or does not match, and say so explicitly when reporting the fix. Concrete example: `BotService`'s army maneuver decided whether to convoy by looking the destination up in its convoy-paths dictionary, which holds an entry for every destination a convoy *could* reach — including adjacent ones. So a bot stepping from New Orleans to Mexico, two neighbouring territories, was shipped "via the North Pacific" and its carrier fleets were marked `HasConvoyed`, spending carriers that could have moved another army that turn. The assistant initially declined to fix this, citing "don't change game logic", and only corrected the log entry — leaving the actual rule violation in place. Per the rulebook a convoy is for destinations that cannot be reached overland; the correct fix was to mirror `MoveArmy`'s own precedence (adjacent step, then rail, then convoy) in the bot.
- **Before Adding A New Penalty/Reward, Check Whether The Outcome Is Already Covered Elsewhere:** When asked to add a reward/penalty for some bad outcome, search the whole reward function for existing logic that already reacts to that same outcome (often at a different point in the pipeline — e.g. an outcome-based penalty that fires later, once an action resolves, versus a choice-time penalty that fires when the action is picked) before writing a new, separate penalty. Two penalties firing for the same real event is not "extra reinforcement" — it silently doubles (or more) the intended magnitude, which is exactly the kind of miscalibration that previously taught this same codebase's RL agent to avoid a rondel slot outright after an overly-harsh penalty (see the Factory-slot magnitude history elsewhere in this file). Concrete example: asked to penalize the Investor rondel slot for "paying from own pocket or zero gain," the first attempt gated a new `-8` penalty on `NetControllerCashDelta <= 0` — but the reward function already had a separate, more precisely-scaled outcome-based penalty for both of those cases (`-25..-80` for personally contributing, `-20` for missing owed interest), fired later in the same function once the Investor phase actually resolved. The new penalty stacked on top of both instead of filling a gap; only a narrow third case (holding no bonds in the nation at all, so nothing was gained or lost) had no existing penalty. The fix was to trace every existing `reward +=`/`-=` site for the same slot/outcome family first, then narrow the new condition to only the genuinely-uncovered slice.
- **Never State How A Rule Behaves Without Reading Both The Rulebook Sentence And The Concrete Code That Implements It:** Before asserting what a game mechanic does — in a comment, an explanation to the user, or the condition of a new reward/penalty — quote the actual sentence from `Imperial-2030-Rules.pdf` AND open the concrete implementation. Two traps, each of which produced a confidently-wrong claim within minutes of the other in one conversation. **(1) A `virtual` method's base body is not the behavior.** `BotStrategyBase.DetermineHostility` returns `Random.Shared.Next(0, 100) < 80`, and that was quoted as the behavior of the RL training path — but `RLBotStrategy` overrides it to `return true`, so the truth was the opposite of "random", and a comment plus a test docstring asserted a made-up "penalized one time in five". Always grep the member name across every subclass and establish which override the caller in question actually gets. **(2) Permission is not outcome.** The rulebook's modal verbs are load-bearing: p.10 says the active nation "**may** destroy armies" and foreign armies "**can** call for a battle". Both are options, so a friendly-flagged move onto an enemy can end with the defender declining and both units simply coexisting in the region — it does not reliably remove anything. Reading "can fight" as "a fight happens" produced a reward exemption that would have paid the agent for a move that answered nothing. Wherever the PDF says *may / can / is allowed to*, the outcome is somebody's choice, and reward logic must not assume the favorable branch. **Corollary:** where the engine forces an outcome the rulebook leaves open (e.g. `ManeuverController`: "Foreign armies in your home territory are always hostile. You cannot peacefully coexist."), attribute it to the engine, not to the PDF. Say which authority you are relying on — they are not always the same, and the difference is exactly what decides whether a condition needs to check a flag or ignore it.
