# Agent Rules

- **Cleanup Temporary Files:** Always proactively remove any temporary scripts (e.g., Python scripts, text files) or intermediate media files (like extracted PNGs) created during debugging or troubleshooting before concluding a task.
- **Backend Bugfixes (Test-Driven):** When fixing a bug on the backend, always write a failing test first to reproduce the issue, verify that it fails, then implement the code fix, and finally run the test again to ensure it passes (green).
- **Cross-Platform Compatibility:** Ensure all written code (including scripts and file paths) is fully compatible and works seamlessly across both Windows and Linux operating systems.
- **Build Before Completion:** Always compile/build the project to ensure there are no compilation errors before reporting that a task is done.
- **Extract Constants:** Always extract constants to avoid magic numbers and strings.
- **Run Tests on Backend Changes:** Run targeted tests (e.g., dotnet test --filter <SpecificTest>) during development, and only run the full test suite (dotnet test) during final verification before completing a task.
- **Entity Model Changes & Migrations:** When adding or modifying public properties on EF Core entities, never leave them half-done. Explicitly mark runtime/transient properties with `[NotMapped]` or, if they are intended to be persistent database columns, always generate both EF Core migration files (`SqliteApplicationDbContext` and `SqlServerApplicationDbContext`). Migrations must be applied automatically from code on application startup (via `DbSeeder.SeedAsync` / `context.Database.MigrateAsync()`) and never require manual `dotnet ef database update` CLI commands, ensuring zero-configuration deployments across Azure App Service, Windows, and Linux VPS servers.
- **Diagnose & Report Errors First:** When troubleshooting runtime errors, bugs, or crashes, always inspect logs, terminal output, or stack traces to identify the exact root cause first. Present the factual error diagnosis clearly to the user before making code changes or guessing fixes.
- **Plan & Approval Required for New Features:** Never begin coding or implementing any new feature, architectural change, or non-trivial modification without first writing a detailed implementation plan (`implementation_plan.md`) and obtaining explicit approval from the user.
- **Verify & Maintain Comments in Modified Areas:** Whenever modifying or refactoring code, inspect surrounding and inline comments in the affected scope. Preserve valid comments, update comments that need adjustment to reflect code changes accurately, and remove comments only if they are genuinely obsolete or no longer applicable. Never silently drop or strip valid inline comments during refactoring.
- **Preserve Existing Logging & Telemetry:** Never comment out, remove, or alter log statements (e.g., `_logger.LogInformation`, `_logger.LogWarning`, `_logger.LogError`, console outputs, or telemetry) without explicit instruction from the user. Logging is essential for user inspection, progress monitoring, and debugging.
- **Strict Scope Discipline & No Unsolicited Suppressions:** Never suppress, comment out, disable, or bypass working features, debug logs, or diagnostics to reduce terminal output, optimize I/O, or silence warnings unless the user explicitly requests it.
- **No Speculative Feature Expansion or Hallucinated Action Spaces:** Never invent, expand, or hallucinate action spaces, decision branches, policy masks, or training overrides based on speculation or ungrounded assumptions. All logic and bugfixes must strictly adhere to the actual codebase architecture and explicit user specifications.
- **Game Rules Are Imperial 2030, Not Classic "Imperial":** The authoritative rules are `Imperial-2030-Rules.pdf` at the repo root. This is a *different, rebalanced* game from the classic 2006 "Imperial" board game — it has only six nations (Russia, China, India, Brazil, USA, Europe), not Imperial's Austria-Hungary/Italy/France/Germany/Great Britain/Russia. When reasoning about or implementing game mechanics, verify against the PDF rather than assumption or general "Imperial"-family knowledge — a hallucinated comment referencing a nonexistent "Austria/Europe" investor card was a real bug caused by exactly this confusion.
- **Always Preserve Old RL Model Performance:** When changing RL training/inference code (`RLBotStrategy.cs`, `TcpTrainingServer.cs`) in ways that touch the state vector or action space, existing already-trained `.onnx` models must keep working at their original, undegraded performance — never silently fall back to random or heuristic play. Concretely: only ever *append* new floats/actions at the end of the existing layout (never splice into a per-nation loop or insert before other fields — that reindexes everything downstream and breaks byte-for-byte compatibility with what old models were trained on), and add a matching size guard at the point of ONNX inference (compare the loaded model's actual input/output width against the current vector/action-space size) so an older model gets a truncated prefix — a byte-for-byte reproduction of its original training input — and runs real inference, instead of silently degrading. After any such change, verify old models are still using inference (not the random fallback) by checking training-server action counters stay non-zero and win-rate tests return to their pre-change baseline.
